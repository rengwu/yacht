## Question 9

```text
Round: Round 2 — what you see during the day
Question: What should remain visible in the menu bar when the dropdown is closed?
Description (Markdown source):
We have settled on four to eight accounts and a menu bar utility. Showing every account continuously uses more menu bar width; there is no meaningful combined quota percentage across separate subscriptions.
Recommendation: Show one account you explicitly choose, with its percentage. Keep that choice stable instead of silently switching to whichever account is most depleted.
Options: An icon only; all usage appears on click / An icon and usage for one account I choose / Short usage figures for every account I choose to show
Selected: (notes only)
Notes: customizable. supports short usage figures for each enabled account.
```

Recommendation: Use an explicit remaining value, such as 70% left, to match the question you want the app to answer.

## Question 11

```text
Round: Round 2 — what you see during the day
Question: Which quota windows should be visible immediately when you open the dropdown?
Description (Markdown source):
Providers can report different windows. Some accounts have a short session limit and a weekly limit; another may report only one. A missing window must not be invented.
Recommendation: Show all reported windows for each account in compact rows. A weekly limit can matter even when the short window has plenty left.
Options: All reported windows for every account / Only the provider's primary window; reveal the others on demand / One window type at a time, switched for the whole dropdown
Selected: All reported windows for every account
Notes:
```

## Question 15

```text
Round: Round 2 — what you see during the day
Question: How fresh should readings stay while you are not opening the dropdown?
Description (Markdown source):
The existing pulled providers use roughly one-minute polling while active and fifteen-minute polling while idle, with a refresh attempt on opening. Claude reads local snapshots. Keeping figures fresh has a background-work cost; the precise implementation will be measured later.
Recommendation: Retain adaptive updates as the initial policy, then measure their cost for four to eight accounts before setting the final resource budget.
Options: Adaptive background updates, plus refresh on opening / Slow background updates, around every five minutes, plus refresh on opening / Refresh only when I open the dropdown or request it
Selected: Adaptive background updates, plus refresh on opening
Notes:
```

## Question 17

```text
Round: Round 2 — what you see during the day
Question: After a saved reset time passes, what should the app show before another reading arrives?
Description (Markdown source):
The existing implementation infers an empty window after its reset. That can be misleading if the account has already been used elsewhere. Restarting the design gives us a chance to choose this explicitly.
Recommendation: Show reset passed or awaiting update without claiming a new percentage until the provider confirms it.
Options: Unknown percentage with reset passed or awaiting update / Assume full capacity, explicitly marked as estimated / Keep the old percentage, explicitly marked as expired
Selected: Unknown percentage with reset passed or awaiting update
Notes:
```
